## Plan
Approved by Sham on 2026-11-12 (project thread "Build side backlog tasks in parallel"). Split in two because the chart app (M2-05) is being built by the main session.

Part 1 (this PR), in `contexts/indicators/src/domain`:
1. `settings.ts`: `checkSettings(inputs, given)` refuses undeclared keys, wrong types, fractions for whole numbers, values outside min..max or off the step grid and options not on the list, with a reason per field; missing keys take their default. `settingsKey` gives a stable text form for the engine's cache key (M3-04).
2. `settings-dialog.ts`: `settingsDialog(definition, current?)` describes the dialog as plain JSON, one field per input (number box with limits and step, switch, or drop-down), with current values and defaults.

Part 2 as first planned: a React dialog in the chart app that draws `SettingsDialog`, and the route that receives settings resolves the principal, checks the access policy (like `/bars`, rule 4), calls `checkSettings` and returns its errors as a 400.

Part 2, detailed plan (2026-11-14, waiting for Sham's approval). What I found: no route takes indicator settings yet (the run route is M3-05, per M3-04's handoff), `apps/platform` does not depend on `@aia/indicators`, and the browser may import only `@aia/client-contract` and the kernel (`boundary.test.ts`). So the dialog's shape has to become part of the client contract.

1. **Client contract (a contract addition, so I'm asking first):** `contexts/client-contract/src/domain/indicator-settings.ts` gets the wire types: `IndicatorSettingsDialog` (fields: number / switch / select, the same shape as part 1's `SettingsDialog`), `IndicatorsResponse` (`{ indicators: [{ id, name, dialog }] }`), `SettingsAccepted` (`{ indicatorId, settings, dialog }`) and the 400 body `invalid_settings` with `fields: [{ key, code, message }]`. `@aia/indicators` stays unchanged. The platform hands its values on as the contract types, so TypeScript catches any drift between the two.
2. **Platform routes** (`apps/platform/src/indicator-routes.ts`, mounted when `ServerDeps.indicators?: Pick<IndicatorRegistry, 'get' | 'list'>` is given). Both resolve the principal first (401) and count against the read limit, like `/bars`:
   - `GET /indicators`: each registered indicator with its dialog at defaults.
   - `POST /indicators/:id/settings` with `{ settings }`: unknown id gives 404 `not_found`; otherwise `checkSettings`, then 400 `invalid_settings` with every field error, or 200 with the checked settings (defaults filled, values snapped to the grid) and the dialog refilled with them. M3-05's run route reuses the same helper (`acceptSettings`), so there is one server-side check.
   - Plan check: the placeholder plans (T-02) have no indicator entitlement, so any signed-in principal, human or agent, may list indicators and check settings. Per-plan indicator access waits for InvestAnswers' plans (OI-21). This goes into the decision record as a new temporary entry.
   - `main.ts` passes an empty registry for now: no indicator exists in this repo until M3-05 brings the SMA from `agentic-investanswers-indicators`. `e2e-server.ts` registers a test-only definition that declares one input of each kind (int, float, bool, choice, source) and has a trivial step. It is not an indicator, it is only there so the e2e test can draw a dialog.
   - Tests (`indicator-routes.test.ts`, fastify inject): 401 without a principal; the listing; out-of-range, off-step, wrong-type, unknown-key and not-an-option values each refused with a 400 and the field named; a valid body accepted with defaults filled; unknown id 404; the agent principal gets the same answers.
3. **Chart app:** `data/platform-client.ts` gets `indicators()` and `checkSettings(id, settings)`. `ui/SettingsDialog.tsx` draws any `IndicatorSettingsDialog` (a number box with min/max/step, a switch, a drop-down, help text, "Reset to defaults"). The number box uses the HTML limits as a convenience, while the server makes the decision and its messages appear under each field. A pure `ui/settings-form.ts` (form values to a settings body, error body to per-field messages) gets Vitest tests. The toolbar gets an "Indicators" menu, hidden when the list is empty; Apply posts the settings and, on 200, keeps the checked settings in app state (M3-05 draws them). Vite proxy: add `/indicators`.
4. **E2E (Playwright, e2e server):** open the menu, open the test indicator's dialog, check that the five fields render with their limits and defaults, enter an out-of-range value, Apply, and see the server's message under that field; then enter a valid value and the dialog closes.
5. **Docs:** the route list in `server.ts` and `docs/architecture.md` (indicator engine section, Vite proxy list), the decision record entry from step 2, and the card handoff.

Done check: platform tests prove the server refuses out-of-range values; e2e proves the dialog renders from the schema; `pnpm check` green. Neither bars nor indicator output change, so parity commands don't apply (and `pnpm parity:indicators` doesn't exist yet).
