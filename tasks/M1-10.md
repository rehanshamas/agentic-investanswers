# M1-10 Rebuild check: re-cook every timeframe from raw and diff against stored cooked bars

GitHub issue: #16
Lane: A      Depends on: M1-06 (done, #62)      Owner inputs: none pending

## Goal
`pnpm rebuild-check` re-cooks every cooked timeframe from raw 1-minute bars in memory, compares the result bar for bar with the cooked store, and reports any difference. It writes nothing. This proves CLAUDE.md rule 3: cooked is always rebuildable from raw.

## Plan
**0. Fix found while reading: `CookIntraday.applyNewMinutes` would wipe cooked partitions.** It `put`s only the rebuilt bars, but the store's `put` replaces each partition (a month) whole, and the port says the caller must pass every bar of a partition it touches. On S3, one new minute would leave that month's 5m file holding one bar. M1-06's tests use a merging in-memory store, which hides it. No caller exists yet (M1-05 will be the first), so no data is damaged.
- **Fix:** read each touched partition (`getPartition`), replace the rebuilt bars in it, and write the whole partition back.
- **Tests:** a test store with S3's replace-the-partition semantics, which fails before the fix and passes after; and "one new minute leaves the rest of the month intact".

**1. `pnpm cook`: fill the cooked store from raw** (needed first; otherwise the check would compare nothing)
- `apps/hydration/src/cook.ts`, run as `pnpm cook [--symbol] [--timeframe] [--from 2024-11-01] [--until]`.
- It works month by month. Each month's raw minutes are read once (through `RawMinuteSource` from the `coinbase` prefix), rolled up to 5m/15m/1h/4h, and each timeframe's partition is written whole with `put`. Memory stays bounded.
- It uses the existing `rollUp` and the store. Cooked may be overwritten (rule 3), so re-running is safe.
- 1D/1W/1M are not cooked until M1-08. The command says so rather than half-doing them.

**2. Rebuild check: pure diff plus a use case, writing nothing**
- `domain/rebuild-diff.ts` (pure): `diffBars(rebuilt, stored)` is an exact comparison by time. It counts matched, differing, missing from the store, and stored-but-not-rebuildable, and keeps the first difference. Unlike parity there is no window logic: a partition must equal its rebuild exactly.
- `application/rebuild-check.ts`: `RebuildCheck.run(instrument, from, until)`.
  - For each month partition in range, read raw once, roll up each intraday timeframe in memory, `getPartition` the stored one, and diff.
  - A month with raw data but no cooked file counts as a difference ("not cooked"). So does a cooked file with no raw behind it.
  - It never calls `put`.
- `adapters/rebuild-report.ts`: a table per symbol × timeframe (partitions, bars, differences), the first difference for each failure (reusing the parity report's difference block), and a verdict `REBUILD CHECK OK: 0 differences` or `FAILED: n differences`.

**3. `pnpm rebuild-check [--symbol] [--from] [--until]`**, in `apps/hydration/src/rebuild-check.ts`. Exit codes: 0 only when something was checked and there are 0 differences; 1 for differences; 2 when stores are unreachable.

**4. Tests (in memory, CI)**
- Cook then check gives 0 differences.
- One stored bar changed is found, with its time and field.
- A deleted cooked partition is found as not cooked.
- A cooked partition without raw is found.
- The check performs no writes (the store records calls).
- A month boundary and a gap minute are handled.
- Plus the step-0 regression tests.

**5. Done-check run (local MinIO, the 738 backfilled days per symbol)**
- `pnpm cook --from 2024-11-01`, then `pnpm rebuild-check` must report 0 differences.
- Then `pnpm parity --fidelity` as a bonus: source fidelity for 5m–4h becomes visible for the first time.

**Out of scope:** cooking D/W/M and stock sessions (M1-08; the check picks them up automatically once M1-08 cooks them), scheduling the check in AWS.
