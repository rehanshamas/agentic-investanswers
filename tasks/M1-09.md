## Plan
**1. What "expected" means, per market hours (`domain/gaps.ts`, pure)**
- Crypto: every minute of the UTC day.
- Stocks: the regular session of that New York date from the M1-12 calendar (13:00 close on half days), and nothing on holidays.
- Pre- and after-hours minutes are never expected, so a quiet pre-market minute is not a gap.
- `findHoles(bars, expected)` returns the missing minutes, grouped into runs.

**2. Repairing without editing raw: write-once gap-fill files** (a raw store change; see the question below)
- A raw day stays the single file it was written as.
- Minutes found later are stored in a **new write-once file beside it**, `raw/<provider>/<symbol>/YYYY/MM/DD.fill-<n>.parquet`, with `n` = 1, 2, … and each written with `IfNoneMatch: '*'` like the day file.
- `getDay` returns the day file merged with its fills. Callers (cooking, the rebuild check, parity) see one day, unchanged.
- A fill may hold only minutes absent from the day and its earlier fills. Anything else is refused, so nothing in raw is ever replaced.
- The cost is one extra LIST per day read. Locally it's negligible; for S3 later, a fill index could replace it.

**3. `application/gap-repair.ts`: `GapRepair.run(instrument, range, now)`**
- For each day in range, compare raw with what's expected:
  - a missing whole day goes through the normal `Backfill` path;
  - a day with holes is a suspect.
- Suspects are re-fetched from the provider: Coinbase per day, Massive 40 days per request through `fetchDays`. Each hole minute is then one of:
  - **filled:** the provider has it, and it goes into a fill file;
  - **confirmed empty:** the provider has no bar either, a minute with no trades. Nothing is written.
- Also reported, without writing: minutes where the provider now differs from what raw holds (late corrections). Raw is never changed for those.
- Returns the months touched, for re-cooking. It respects the same settle rules as the backfill (1 h crypto, 2 days stocks).

**4. `pnpm gaps [--symbol S] [--from] [--until] [--dry-run]`** (`apps/hydration/src/gaps.ts`)
- The default range is the last 7 settled days. `--from 2024-11-01` scans everything.
- It repairs, then re-cooks each touched month with `CookIntraday.cookPartition` (crypto). Stocks are re-cooked once M1-08 exists.
- It prints per symbol: days scanned, suspects, filled, confirmed empty, differing, and the months re-cooked.
- Exit codes: 0 when there are no unresolved gaps, 1 when a re-fetch failed, 2 on a setup error.

**5. Tests (CI, in memory)**
- **The done-check:** store a day with minutes deleted; the fake provider still has them. They are found, written as a fill, and `getDay` returns the full day. `cookPartition` re-cooks, so the cooked 5m/1h bars include them. The rebuild check then shows 0 differences.
- Minutes the provider also lacks count as confirmed empty, and nothing is written. A second run writes nothing.
- A missing whole day is re-fetched.
- Stocks: a pre-market hole is ignored and a session hole is checked; a half day ends at 13:00; holidays are skipped.
- Fill rules: a fill overlapping the day or an earlier fill is refused; two fills are merged in order.

**6. A real run on the local data**
- `pnpm gaps --from 2024-11-01` for all four symbols. I expect most crypto holes to come back confirmed empty, since the backfill read the same API.
- Then a demonstration on real data **under a scratch symbol**: copy one BTC day into `raw/coinbase/BTCUSD-GAPTEST/` with 10 minutes removed, repair it against Coinbase, check the merged day equals the original, and delete that scratch prefix afterwards. Real raw files are never touched.

**Out of scope:** stock re-cooking (M1-08), live-stream gap marking (M1-05/M1-07b will record disconnect windows, which this detector then repairs), scheduling.
