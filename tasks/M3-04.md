# M3-04 Indicator engine: runs server-side, caches by indicator+version+instrument+tf+settings, extends by one bar

## Goal
Run indicators on the server, cache each run, and extend a cached run by the bars that closed since instead of recomputing it, returning only drawn points.

## Plan
Approved by Sham on 2026-11-13 (project thread "Build side backlog tasks in parallel"), including a run of at most about 5,000 bars.

1. `domain/run-window.ts`: where a run starts. Pinned to a grid of 5,000-bar blocks (the block before the newest bar's), so runs rebuilt after a cache miss start at the same bar and agree exactly.
2. `domain/state-codec.ts`: state to text and back, keeping NaN and infinities.
3. `application/indicator-bar-source-port.ts` (closed bars; the app wires it to the data-access interface, M1-16) and `application/indicator-output-cache-port.ts`.
4. `application/indicator-engine.ts`: `IndicatorRegistry` (definitions checked at start-up) and `IndicatorEngine.drawn(request)`: check settings, read the newest bar, resume the cached run if its last bar is unchanged and commit only newer bars, otherwise run from the start; preview the forming bar; store the entry.
5. Adapters: memory (tests) and Redis (`ind|` keys with a 7-day TTL), one contract test for both.

## Handoff
**Done.** Engine, registry, ports, memory and Redis caches, and tests (105 in the context, Redis contract tests run against a local Redis). After review on #89: a cache that is down or an unreadable entry counts as a miss and the engine recomputes; writes are best effort; a non-numeric `limit` falls back to 500. `pnpm check` green.

**Surprises.**
- "At most the last 5,000 bars" as a trailing window would make results depend on when the cache was last filled, because ATR-style indicators carry history forward. The start is pinned to a grid instead, so a run covers 5,000 to 10,000 bars and is the same however it was built. Told Sham in the PR.
- JSON turns NaN into null, which would silently change a ported indicator's next value after a cache round trip; `state-codec.ts` keeps them.

**Left for later tasks.**
- M3-05: wire the engine in `apps/platform` (a route that resolves the principal, checks the access policy, and maps `invalid_settings` to a 400), with an adapter from the data-access interface (M1-16) or market-data's readers to `IndicatorBarSourcePort`; push forming-bar previews with live updates.
- Only the cached last bar is compared with the store. A change to older bars with the last one unchanged is not detected: re-cooks (`pnpm cook`) and gap repair or backfill (`pnpm gaps`, `pnpm backfill`, M1-09) should drop `ind|` keys for the instruments they touch, as they drop the recent-bars windows. The M1-15 compactor need not (it rebuilds from the same raw data).
- The M3-05 route must parse `limit` the way `HistoryQuery` does (the engine only guards against NaN).
- Run-window blocks are sized in wall-clock time, so a 1m stock block holds about 1,300 bars, not 5,000. Check against the ATR warm-up when it is ported.
- Scroll-back older than the newest 2,000 points (M2-06) needs a "before" on the request; the engine can recompute that range from the run start.
