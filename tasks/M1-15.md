# M1-15 M1 scale-out: no bottleneck or dead end in the live data path

## Plan

**What the code does today, per instrument, per live minute**

| Step | Storage work | At 500 instruments |
|---|---|---|
| Raw: store the closed minute | 1 PUT (one object per minute) | 500 PUTs a minute: fine |
| Cooking: rebuild the 5m, 15m, 1h and 4h bars | for each of the 4 timeframes, **GET and PUT the whole month file** (`writeMerged`); a month of 5m is 8,640 bars | 2,000 full-file rewrites a minute, growing with the month; one writer per instrument only, or writes are lost |
| Cache and announcement | 5 Redis scripts, 1 publish | fine |
| Reading today's minutes from raw (cold `/bars` 1m, cooking after a restart) | **1 LIST + up to 1,440 GETs**, one per minute object | slow cold reads, on every platform instance |
| Processes | one `pnpm live` streams every instrument | no way to split |

So two things grow with time and scale: the month rewrites, and the minute-object reads. Plus one hard limit: a single process.

**Steps**

1. **Measure first.** Pull the per-minute work out of `live.ts` into a `LivePipeline` (composition only: store, cook, cache, announce, in that order). `live.ts`, the replay tests and the load test then all run the same code.
   - `pnpm load-hydration --instruments 500 --minutes 5` drives it with simulated instruments at the real minute rate, against MinIO and Redis. Storage and Redis are wrapped in counters.
   - It prints requests per minute by kind (PUT, GET, LIST), bytes, and how long each minute takes from close to announced (p50, p95). It also prints a projection to 2, 50 and 500 instruments: requests per day and the S3 cost at list prices.
   - It runs once on today's code as the baseline, then again after each change.
2. **Cooked holds settled days; the newest part is cooked on read.**
   - Each instrument gets a **cooked watermark**: everything up to it is in the cooked store.
   - The live path cooks each new minute **in memory** (from the minutes it already holds), then updates the cache and announces, as now. It no longer writes cooked files every minute.
   - A **compactor** in the same process writes each settled UTC day into the cooked partitions once, then moves the watermark. That is one rewrite per timeframe per day, not per minute.
   - Readers (`RecentBars`) take stored bars up to the watermark, and roll up the rest from raw 1m with the same `rollUp`. That rest is at most a day or so, more if the compactor fell behind, and it is still correct then.
   - The cache is unchanged: it still holds the newest 2,000 bars and is still only a shortcut.
   - `pnpm cook`, `pnpm gaps` and `pnpm backfill` keep writing cooked directly, and move the watermark.
   - The rebuild check covers everything up to the watermark.
3. **Raw: an hour file for live minutes.**
   - Once an hour has closed, the live process writes that hour's minutes as one write-once file (`DD.live/HH.parquet`). It is built from the minute objects already stored, not from memory.
   - Readers use the hour file when it exists, otherwise the minute objects. So today costs at most about 24 hour-file GETs plus up to 60 minute GETs, not 1,440.
   - Minute objects are never edited or deleted, and the day file from backfill still supersedes both. Same rule as today's day file and gap fills, so raw stays write-once.
4. **Shards.**
   - `pnpm live --shard 2/8` streams only the instruments that hash to shard 2 of 8, stable by symbol. The feed plan can pin an instrument to a shard.
   - Each instrument has exactly one writer, so the single-writer assumption holds. Each shard compacts its own instruments.
   - The gateway tracks sequence numbers **per publisher**, so several shards announcing at once is normal, not a gap. A new publisher's first announcement is a resync, so charts drop forming bars a dead shard left behind.
   - Today it treats any change of publisher as a gap, which would resync charts constantly with more than one shard.
5. **Tests.**
   - settled plus tail equals a full re-cook from raw, including across a midnight and with the compactor a day behind
   - a crash mid-compaction leaves readers correct
   - hour files: equal to the minute objects; a missing or late hour falls back
   - shards: every instrument in exactly one shard
   - gateway: several publishers; a new publisher resyncs
   - the replay test unchanged, through `LivePipeline`
6. **Done-check.**
   - `pnpm load-hydration --instruments 500 --minutes 5` against MinIO and Redis: every minute handled within a few seconds (p95 reported), cooked writes per minute 0 outside compaction, raw writes 1 per instrument per minute, and no growth as the partition fills.
   - The before and after projections go in the Handoff and in `docs/architecture.md`.

**Decisions (Sham, 2026-11-13: "move ahead" on the recommendations)**
1. Cooked holds settled days; the newest part is cooked in memory for live and on read from raw (step 2).
2. Raw hour files for live minutes, write-once, superseding the minute objects for reads (step 3).
3. Shards by a stable hash of the symbol, with an optional pin in the feed plan.
4. Three PRs under this card: **M1-15a** (measurement, `LivePipeline`, cooked settled plus tail), **M1-15b** (raw hour files), **M1-15c** (shards, gateway sequence per publisher).
