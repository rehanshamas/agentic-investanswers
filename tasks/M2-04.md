# M2-04 Live gateway: one WebSocket per browser, subscribe per visible instrument/tf, batched updates

GitHub issue: #21
Lane: A      Depends on: M2-02      Owner inputs: none

## Goal
Push each new or updated bar to every browser whose chart shows that instrument and timeframe, over one WebSocket per browser that carries all its subscriptions, with updates batched, in order, and never ahead of the store.

## Plan

**What exists.** `pnpm live` (hydration process) stores each closed minute, cooks it, and calls `RecentBars.onBarClosed` with the BarClosed events: the 1m bar, plus each 5m to 4h bar it rebuilt, which may still be forming. Nothing leaves that process. `apps/platform` runs Fastify with `GET /bars`. `HistoryQuery` owns parameter rules, what is served (`whyNotServed`) and display units. `@aia/access` has the principal resolver and policy ports. The live stream emits **closed minutes only**, with no forming-minute event (see question 1).

**Steps**

1. **BarClosed over Redis pub/sub** (market-data). Add `LiveBarsPort` (`publish(events)`, `subscribe(onEvents, onGap)`) in application, a `RedisLiveBars` adapter, and an in-memory one for tests.
   - One channel, `bars:live`. One message per closed minute per instrument holds that minute's events: values as scaled integer strings, plus a per-publisher sequence number.
   - The adapter reports a gap when its connection drops or a sequence number is skipped. Pub/sub does not replay what was missed.
   - Redis is already in our stack, and the architecture names pub/sub as the link between the two processes, so no new service.
2. **Publish only after the cache update** (`apps/hydration/src/live.ts`). The order is store → cook → cache → publish. A browser that gets a live bar and then reads `/bars` sees that bar, so live never runs ahead of the cache or the store. If publishing fails, the minute is logged and skipped, and clients fill the hole on their next resync (step 4).
3. **`LiveGateway`, framework-free** (`contexts/market-data/src/application/live-gateway.ts`). It holds a subscription registry (instrument and timeframe → connections) and a per-connection outbox, and it is tested with fake connections.
   - `subscribe(conn, instrument, tf)` validates with the same rules as `/bars`: `bad_parameter`, `unknown_instrument`, `timeframe_not_served`.
   - **Batching:** updates collect per connection and flush every **100 ms**, only when something is pending. A bar repeated within one batch keeps only its newest value.
   - **Order:** one subscriber, processed in sequence, and per connection a send queue in arrival order. For each instrument and timeframe a client gets updates in publish order. Bar times never go backwards, except when a newer value replaces the same bar.
   - **Gap:** after a pub/sub drop or a skipped sequence number, every connection gets `{ type: 'resync' }` and refetches its newest page from `/bars`.
   - **Slow clients:** when a socket's buffered bytes pass a limit (proposed 1 MB), the gateway closes it with code 1013. The client reconnects and resyncs, so the server never buffers without bound.
   - **Cap:** at most **20 subscriptions** per connection. M2-10 can tune this with the other safeguards.
4. **Wire protocol** (`adapters/ws/live-protocol.ts`, typed, also used by the load test and later by M2-05).
   - Client to server: `{ op: 'subscribe' | 'unsubscribe', instrument, tf }`.
   - Server to client:
     - `{ type: 'subscribed', instrument, timeframe }`
     - `{ type: 'bars', updates: [{ instrument, timeframe, bar: { time, open, high, low, close, volume } }] }`, in the same display units as `/bars`, sharing `displayBar`
     - `{ type: 'resync' }`
     - `{ type: 'error', code, message, instrument?, timeframe? }`
   - **Client contract:** subscribe first, then load `/bars`, then apply updates by replacing on bar time. An update that arrives before the page loads is harmless.
5. **Route** (`apps/platform`): `GET /live`, upgraded to a WebSocket.
   - The principal is resolved at the upgrade: 401 is refused before the upgrade.
   - The policy `canReadBars` is checked on every subscribe (`forbidden`), as the architecture requires for WebSocket subscriptions.
   - Browsers cannot set headers on a WebSocket, so the resolver gets the `Authorization` header or a `token` query parameter. M2-08 decides which one is real. Until then, `AIA_DEV_AUTH=1` applies as for `/bars`.
   - Mounted on the same `buildServer`, sharing one Redis subscriber per process.
6. **Load test**: `pnpm load-live [--clients 1000] [--seconds 60]` (`apps/platform/src/load-live.ts`).
   - It starts the real server on the in-memory `LiveBars` (with `--redis`, on the local Redis) and opens N WebSocket clients. Each client subscribes to 1 to 4 random pairs out of BTC and ETH × 1m to 4h.
   - A fake publisher sends minute events much faster than real time (proposed: one "minute" every 50 ms per instrument), each carrying a sequence number.
   - **Checks:**
     - every client receives every update for its pairs
     - updates arrive in publish order for each pair, with no gaps and no duplicates beyond replacements
     - nothing is received for pairs a client did not subscribe to
   - It prints p50, p95 and p99 latency from publish to receipt, plus messages per second. It exits non-zero on any order or loss failure.
   - A small version (100 clients, a few seconds) runs in `pnpm check` as a Vitest test, so the order guarantee stays tested in CI. The 1k run is the done-check and is recorded in the Handoff.
7. **Tests:**
   - `LiveGateway` unit tests: batching and coalescing, order, unsubscribe, cap, resync, slow-client close, errors.
   - `RedisLiveBars` against real Redis (DB 15, like M2-02), including the gap after a reconnect.
   - Route tests through the real Fastify server: 401 at the upgrade, 403 on subscribe, error codes.
   - An end-to-end test through the replay of `pnpm live`, where hydration's publish reaches a WebSocket client after the cache holds the bar.
   - A local smoke run with `pnpm live`, `pnpm platform` and `websocat`.

**Questions for Sham**
1. **What does the live bar show between minute closes?** The pipeline knows a minute only once it has closed. So with this plan, the chart's newest bar updates **once a minute**, about 2 to 3 s after the close (the 1m bar plus every higher-timeframe bar it extends). That bar is always a stored bar and matches `/bars` exactly. A bar that ticks with every trade needs hydration to publish the **forming minute** too, for example once a second from the live stream's trade buckets. That bar is not stored, would be marked `forming`, and changes `contexts/hydration`'s `LiveStream` (a new event). **Recommendation:** closed minutes only in M2-04, keeping store-then-publish strict, and forming minutes as a follow-up task if the client wants trade-by-trade ticking. The Friday gate's "live bars tick" holds either way.
2. **New dependency: `@fastify/websocket`**, the official Fastify plugin wrapping `ws`. The load test's clients use `ws` directly. Approve?
3. **Defaults:** a 100 ms batch window, a cap of 20 subscriptions per connection, and a 1 MB send buffer before a slow client is dropped. Fine?

**Out of scope:** real sign-in (M2-08), plans (M2-09), rate limits (M2-10), the chart's client code (M2-05), freshness measurement (M2-07), stocks and 1D/1W/1M (served once M1-08 cooks them; the gateway already uses `whyNotServed`).
