# M1-14 Split parity: exact build parity, reported source fidelity

GitHub issue: #67
Lane: A      Depends on: M1-03 (done, #65), M1-04 (in review, #66; this branch is stacked on it)      Owner inputs: none pending

## Goal
Make `pnpm parity` two checks. **Build parity** is exact and blocking: TradingView's own bars, rolled up by our code, must equal TradingView's higher-timeframe exports. **Source fidelity** is reported, not blocking: our provider bars against the exports, with match rates per field.

## Why
Decided by Sham on 2026-11-09, from M1-04's first real comparison. Coinbase 1m vs the exports differs in volume on 1–10% of bars, because TradingView misses trades (up to ~3.5% per hour), and in price only at minute boundaries. Exact volume parity is impossible from any source but TradingView itself. What parity must prove is that *we build bars the way TradingView does*, and build parity tests exactly that, with no tolerance.

## Plan
**1. Build parity, `domain/build-parity.ts` (pure)**
- `buildParity(instrument, target, sourceBars, targetBars, calendar?)` rolls the source export up to the target with the existing `rollUp`, then compares with `compareBars`. Exact, no tolerance.
- `rollUp` already buckets by each bar's open time through `alignToTimeframe`, so it works for any finer source whose bars never straddle a target bar. That holds for every pair below, including stock 4h (09:30/13:30) from session-aligned 1h.
- **Source for each target:** the next finer export, chosen for overlap, not depth:

  | Target | Source |
  |---|---|
  | 5m | 1m |
  | 15m | 5m |
  | 1h | 15m |
  | 4h | 1h |
  | 1D | 1h |
  | 1W | 1D |
  | 1M | 1D |

  This is one table in the domain file.
- **Window: only target bars the source fully covers.**
  - The start uses the rule `parityWindow` already has: the first rolled bar is skipped if the source starts inside it.
  - The end: the rolled bar containing the source's last bar is dropped, because it may be partial, and export bars after it are not compared.
  - Skipped counts are reported as today.

**2. Source fidelity: the existing comparison, renamed, plus field rates**
- `compareBars` also returns how many bars differ per field (open, high, low, close, volume), and the largest relative volume difference.
- The report shows a fidelity table: `FILE  WINDOW  BARS  OPEN% HIGH% LOW% CLOSE% VOL%  MAX dVOL%`, where each % is the share of bars equal on that field.
- Not blocking: it never changes the exit code. A store that cannot be reached is a note, not an error, so build parity can still run without MinIO.

**3. `RunParity`**
- `runBuild(instruments, targets)` needs only the export source port, with no stores.
- `runFidelity(...)` is today's `run`.
- A missing source or target export is a NO EXPORT row, as now.

**4. CLI, `apps/hydration/src/parity.ts`**
- `pnpm parity` runs build, then fidelity. `--build` or `--fidelity` runs one only.
- Exit codes: 0 when build parity is exact; 1 when it fails; 2 only for a broken export or bad arguments. Fidelity never moves the exit code.
- Report order: `BUILD PARITY (blocking)` with the table and first differences, then `SOURCE FIDELITY (reported only)`, then the verdict, which names build parity.

**5. Tests (CI, synthetic samples)**
- Build: the samples' 1m→5m, 5m→15m, 15m→1h and 1h→4h are exact. One tampered target bar fails and is named. A source ending mid-bucket does not fail the last bar. A source starting mid-bucket skips the first bar. A missing source export is NO EXPORT. The samples were generated independently in Python, so these are not self-checks.
- Fidelity: field counts, the volume deviation, and the exit code staying unchanged.
- Unit tests for the window clipping and the source table.

**6. Docs**
- `bar-rules.md` "Comparing against the exports": define both checks. Exactness stays and applies to build parity, with the measured Coinbase-vs-TradingView numbers as the reason fidelity is reported.
- `glossary.md`: "Parity" becomes build parity, and "Source fidelity" is added.
- `backlog.md`: the M1-06 and M1-08 done-checks become "build parity green". `plan.md`: the Week 1 gate wording likewise.

**Changes after approval (Sham, 2026-11-09), from the first real run:**
- Recent bars: a bar that closed within 14 days of the newest bar in either export is compared, and a difference on it is excused (RECENT DIFF) rather than failed. A first version skipped recent bars outright, and that left BTC 5m/15m and ETH 5m with nothing to check, because a 1m export reaches back about 7 days at most.
- Approved exceptions: `domain/build-parity-exceptions.ts`, reported as EXCEPTION, never EXACT, and applied only while the bar differs exactly as listed.

**7. Run it on the real exports locally** and report. If TradingView's own timeframes disagree with each other anywhere (for example 1h vs 15m), that is a finding to bring to Sham, not something to tune away.
