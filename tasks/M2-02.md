# M2-02 Cache layer: recent bars per instrument/timeframe in Redis, updated on BarClosed

GitHub issue: #19
Lane: A      Depends on: M1-06      Owner inputs: none

## Goal
Keep the most recent bars of every instrument and timeframe in Redis, so a chart opens from the cache, and keep that cache equal to the cooked store by updating it on every BarClosed.

## Plan

**What exists.** No BarClosed event and no Redis code yet. `pnpm live` (M1-05) writes each closed minute to raw and calls `CookIntraday.applyNewMinutesToAll`, which returns the rebuilt 5m/15m/1h/4h bars (the last of each may still be forming). Redis 7.4 is already in `docker-compose.yml`; there is no Redis client dependency.

**Design (all in `contexts/market-data`, which owns cooked bars).**

1. **`domain/bar-closed.ts`**: the event, in our types only: `{ symbol, timeframe, bar }`. Emitted for the closed 1m bar and for each higher-timeframe bar it rebuilt. A higher-timeframe bar can still be forming, so the event means "this bar's stored value is now this", which is what both the cache and M2-04's live gateway need. Pure, plus `applyToWindow(window, bar, capacity)` (replace by time or append, keep ascending, trim to capacity) so the update rule is unit-tested without Redis.
2. **`application/recent-bars-cache-port.ts`**: `RecentBarsCachePort` with `get(symbol, tf)` → `{ from, bars } | undefined`, `fill(symbol, tf, from, bars)`, `apply(event)`, `invalidate(symbol, tf)`.
   - The cache holds a **window**: every stored bar from `from` to the latest, so a read inside it is a true hit and a gap can't be mistaken for "no bars". `apply` on a cold key does nothing (it never creates a window of one bar); the window is created on the first read miss.
3. **`application/recent-bars.ts`**: use case `RecentBars`.
   - `read(instrument, tf, { before?, limit })`: cache first; on a miss, or if the request reaches older than the window, read the cooked store (1m from `OneMinuteBarSourcePort`, since 1m is not cooked), refill the window with the newest `capacity` bars, and answer. M2-03 calls this.
   - `onBarClosed(events)`: apply to the cache. If a cache write fails, invalidate that key, so the next read refills from the store rather than serving a stale window.
   - Capacity: **2,000 bars per instrument and timeframe** (a constant; about 4 MB in total for 4 instruments × 8 timeframes).
4. **`adapters/redis-recent-bars-cache.ts`**: one sorted set per key `bars:<symbol>:<tf>`, scored by bar time, member = the bar's integers as a compact string; `bars:<symbol>:<tf>:from` holds the window start. `apply` runs as one Lua script (remove at that score, add, trim to capacity, only if the window exists), so concurrent writers can't interleave. All values are our scaled integers; no floats.
   - Integration test against the local Redis, skipped when unreachable, like the MinIO tests. **CI gets a `redis:7.4-alpine` service** so it runs there.
5. **Wiring in `apps/hydration`.**
   - `live.ts`: after the cooked write for a minute, build the BarClosed events (the 1m bar plus the rebuilt bars) and call `onBarClosed`, in the same per-symbol chain, so the cache only changes after the store has.
   - `cook.ts` (a full re-cook of a month): invalidate the cached keys of the instruments it re-cooked, since a window may now be stale.
   - Publishing BarClosed over Redis pub/sub for the platform process is M2-04's (the live gateway consumes it). This task defines the event and the cache side only.
6. **Tests.**
   - Domain: replace vs append, ordering, trim, a late minute correcting a forming bar.
   - `RecentBars` with in-memory fakes: **cache hit** (second read: zero store/source calls), miss → fill, request older than the window → store, cold `apply` ignored, failed write → invalidate.
   - **Replay done-check** (`apps/hydration/src/recent-bars-replay.test.ts`): replay the recorded 32 minutes (`contexts/hydration/test-data/`) through `LiveStream` into in-memory raw and cooked stores and the cache, warm the cache before the first minute, then assert that for 1m, 5m, 15m, 1h and 4h the cache equals the store's newest bars exactly. A second run uses the real Redis adapter when Redis is reachable.
